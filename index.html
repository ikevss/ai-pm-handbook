理论框架

到底变了什么？
第一章

很多 PM 拿着 AI 工具，但思维还是传统的"写需求→评审→排期"。这里帮你识别 3 个核心思维转变。理解"为什么变了"比记住"怎么做"更重要——AI 时代 PM 的核心竞争力不是"会用工具"，而是"能判断 AI 做对了没有"。

核心变化：从「人→人」到「人→AI→人」

过去的协作链

  • PM 写需求 → 设计师出图 → 前端开发 → 后端开发 → QA 测试，每一环都在等人、理解、传递
  • 最贵的环节是沟通对齐——开会、评审、反复确认，沟通成本随人数线性增长
  • 最大风险是做慢了——排期排不上、返工成本高、项目周期等于各环节时长之和
  • PM 的核心能力：想清楚要什么 + 说服别人

现在的协作链

  • PM 描述意图 → AI 生成方案和代码 → PM 判断对不对 → 技术同事把关。生成变便宜了，迭代变快了
  • 最贵的环节是判断 AI 给的对不对——你没说的它会脑补，你说错的它会认真执行
  • 最大风险是做快了但错了且没人发现——AI 一口气做完 80%，你才发现方向错了
  • PM 的核心能力：想清楚要什么 + 定义什么叫做对了 + 能查出它错没错

三个必须切换的思维习惯

思维转变过去怎么做现在怎么做核心
从描述功能
到定义验收		写 PRD："做一个客户列表页，支持搜索和筛选"——AI 会脑补你没说的所有细节写验收标准："搜'张'能搜到张三；搜不到显示'没找到'；两个筛选能叠加；五千条不卡；断网显示重试按钮"写不出验收标准 = 你自己还没想清楚
从一次说清
到小步逼近		文档一次写全，因为返工贵。但 AI 一口气做完 80%，你才发现方向错了，全废说个大概→AI 复述→纠偏→出方案→做一小块→看效果→继续。永远不让 AI 连做三步以上不给你看中间产物每一环都短，每一环都能叫停
从相信交付
到默认怀疑		开发说"做完了"= 可以验收。AI 说"已完成""测试通过"，可信度接近于零追问三句："我怎么自己看到效果？""你测了哪些、没测哪些？""最坏会怎样、怎么退回去？"——答不上来 = 没做完这不是不信任，这是流程
一句话带走：AI 把「实现」变便宜了，于是「判断」变成了最贵的东西。你的价值从"写清楚要什么"转移到了"说清楚什么算对，并且能查出它错没错"。

六个维度的底层变化

文件资产

到底要维护哪些文档？每个文档里面有什么？
第二章

AI 时代的文档写给 AI 看——结构化、无歧义、可直接当 Prompt。文档不再是"沟通工具"，而是AI 的输入指令和自己的干活记录。六份文档，分两档：第一档没有就不行，第二档按需用。

第一档：没有就不行的 3 份

一份给 AI 当 Prompt，一份管理进度，一份追踪变更。覆盖 80% 场景。

① Product SPEC

产品规格——给 AI 看的指令级文档，不是传统 PRD

这个文档直接被喂给 AI 作为 Coding Prompt。写清楚功能行为、边界条件、错误提示——不许模糊。

## 功能：用户登录 - 用户输入手机号+验证码 - 验证码6位数字，60秒过期 - 错误提示："验证码不正确，请重新输入" - 成功后跳转 /home，localStorage存token - 边界：手机号格式校验、60s冷却、网络超时提示

② README.md

项目入口 + 进度看板，PM 和 AI 共同维护

放在仓库根目录。AI 打开仓库第一眼看到它，知道项目在干嘛、做到哪了、怎么启动。

# 项目名 ## 当前进度 - [x] 用户登录 (PR #12) - [x] 首页列表 (PR #15) - [ ] 详情页 (进行中, feature/detail) ## 技术栈 Next.js 16 + Tailwind + Prisma ## 启动方式 pnpm dev ## 约定 分支: feature/xxx · commit: feat:/fix: 组件: src/components/ · API: src/app/api/

③ CHANGELOG.md

变更记录 = 需求追踪，PM 每轮验收后自己写

替代传统的测试报告和需求追踪表。每轮验收完，写三条：做了什么、关联什么、测了什么。

## 2026-08-11 ### feat: 用户登录页 - 手机号+验证码登录 - 新增 /api/auth/send-code, /api/auth/verify - 关联 Issue #3, PR #12 - 测试通过：正常/格式校验/超时/防刷

第二档：按需使用的 3 份

项目变大、团队变多、需要更细的约束时再加。

④ AGENTS.md 或 CLAUDE.md

AI 协作规则——约束 AI 行为的项目配置，相当于"AI 开发规范"

你是一个前端开发专家。 - 使用中文注释 - 组件用 shadcn/ui - 所有API返回 { code, data, message } 格式 - 不要修改 prisma/schema.prisma 除非明确要求 - 每次修改后运行 pnpm lint 检查

⑤ 验收清单

PM 自己测，不是给测试团队的。每轮在浏览器里逐条打勾，测完就是测试报告。

## 登录功能验收清单 - [ ] 正常手机号+正确验证码 → 登录成功 - [ ] 错误验证码 → 提示"验证码不正确" - [ ] 手机号格式错误 → 红色提示 - [ ] 60秒内重复发送 → 按钮灰色倒计时 - [ ] 验证码过期 → 提示"已过期请重新获取" - [ ] 断网点击发送 → 友好提示 - [ ] 登录后刷新页面 → 保持登录态

⑥ 数据模型简述

给 AI 的数据库上下文。AI 能自己读 schema，PM 只需标注业务含义和状态枚举。

## 核心表 User: id, phone, nickname, avatar, created_at Order: id, user_id, status(pending/paid/shipped/done), amount, created_at

核心原则

1. 文档写给 AI 看——结构化、无歧义，比写给人更严格

2. 仓库即项目管理——README 管进度、CHANGELOG 管追踪、Git 管版本，不需要 Jira

3. PM 自己测——验收清单打勾即验收，不需要测试团队

4. 文档越少越好——SPEC + README + CHANGELOG 三件套覆盖 80% 场景

5. AI 能读代码就不写文档——schema 本身是数据文档，组件代码本身是 UI 文档

PM 日常协作流

本地跑项目看效果 → 发现需求 → 写 SPEC → 打开 AI 工具
"按 spec/login.md 实现" → AI 生成 → Review 代码 → 对照验收清单逐条打勾 → Commit + 更新 README 进度 + 写 CHANGELOG

第五章

8 句话术（直接复制用）

开工我要做【X】。做对了的标准是【1、2、3】。这次不做【Y】。你先复述一遍理解，别动手。
要方案先给方案别写代码。说清楚：怎么做、多久、有什么风险、有没有更简单的办法、会碰到哪些现有功能。
限制范围只改【X】，别碰其他任何地方。改完告诉我你碰了哪些功能。
反馈问题【功能】里，我【操作】，期望【结果A】，实际【结果B】。
卡住时停，别改了。告诉我：你试了什么、为什么没成、你现在猜原因是什么、有哪几个可能方向。
要人话看不懂。用三句话重讲，假设你在跟销售同事解释。
验收前我怎么自己看到效果？给我具体步骤：打开哪里、点什么、看到什么算对。
复盘这次哪里绕了弯路？我下次怎么描述能更快说清楚？

最常见的五个坑

① 看起来做完了，其实是壳子

界面全有，点进去是假数据

每次追问"这数据是真的从后台来的吗？"

② AI 自己给自己打分

"测试通过"——但测试是它自己写的

你手动点一遍验收单。不看 AI 的测试报告。

③ 偷偷改了别的地方

让它修 A，顺手"优化"了 B，B 坏了

明确说"只改 A"，改完追问"碰了哪些功能"

④ 越描越乱

一个问题反复改，代码越来越复杂

两次不成立刻停。回到最初，重新想。

⑤ 你以为它记得

聊到后面它忘了前面的约束

关键约束写进文件，定期让它复述目标。

什么该交给 AI，什么不该

放心交给 AI

  • 查资料、竞品调研
  • 整理会议纪要
  • 做原型 / Demo
  • 数据分析和图表
  • 写周报月报初稿
  • 翻译、润色、改格式

口诀：做错了能马上发现的，放心交。

别交给 AI

  • 定优先级
  • 判断客户到底要什么
  • 涉及钱、权限、隐私的最终决定
  • 对外承诺（客户、老板）
  • 拍板要不要上线

口诀：做错了要很久才发现的，必须盯。
