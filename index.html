CHAPTER 01

协作体系：从线性串联到并行AI增强

协作的对象、结构、信息流和决策权在AI时代全部被重构。旧世界靠"信息传递"串联团队，新世界靠"约束对齐"并行多路产出。这一章梳理两种范式逐项对比，并给出每个变化背后的底层逻辑。

旧范式
  • 协作对象：PM→设计师→前端→后端→QA逐级传递。产品经理写完PRD交给设计师，设计师出图交给前端，前端联调交给后端，后端提测给QA。每一环都是人传人，每个人只负责自己那段。
  • 协作结构：线性串联，上游完成才启动下游。整条链路像瀑布一样依次推进，前一个环节不交付后一个环节就无法开工，项目周期等于各环节时长之和。
  • 沟通方式：PRD文档→评审会→站会→1v1。信息靠会议和文档在人与人之间搬运，一份PRD要开评审会、站会、一对一对齐，沟通成本随人数线性增长。
  • 信息流：单向传递，每环都有损耗。需求从上游传到下游，每经过一次转述就丢失一次细节，最终QA拿到的理解和PM最初的想法常常差一大截。
  • 瓶颈：开发资源瓶颈，PM排队。研发产能是硬约束，PM的需求堆在排期队列里等开发档期，优先级本质是在抢有限的工程时间。
  • 决策权：PM提议，工程评估，多轮博弈。技术方案由工程师评估可行性，PM和工程来回拉扯，一个决策要经历提议-评估-反驳-妥协多个回合才能落地。
新范式
  • 协作对象：PM↔AI Agent 为主，PM↔设计师↔工程师 为辅，都带AI。PM直接指挥自己的AI Agent产出，设计师和工程师也各自带着AI同时工作，人与人之间只在关键锚点上对齐。
  • 协作结构：并行展开，各自带AI同时产出，通过锚点层对齐。不再排队等上游，多路同时开工，靠AGENTS.md、Design Tokens、BDD场景这些约束文件在锚点层汇聚，保证产出能拼到一起。
  • 沟通方式：结构化约束文件（AGENTS.md / Design Tokens / BDD场景），AI直接消费。沟通从"人读文档开会讨论"变成"机器直接读取约束文件执行"，语义不再靠口头传递，而是落成可消费的约束。
  • 信息流：AI能秒读任何人代码，信息不对称降低，但产出不一致风险升高。任何人都能让AI读全仓代码理解上下文，信息壁垒被打破；代价是多路并行产出风格不统一，必须靠约束层管控一致性。
  • 瓶颈：对齐成本是瓶颈，多人AI产出必须能拼到一起。生成速度不再是问题，真正的瓶颈变成"多路AI产出能否对齐"——对齐不好就要返工，对齐成本取代了开发资源成为新约束。
  • 决策权：PM直接做技术决策，ADR记录，AI执行，PM验证。PM不再需要等工程评估，自己拍板技术方向，用ADR（架构决策记录）留痕，AI负责执行，PM验收产出是否符合预期。
核心矛盾变化：旧范式核心矛盾是"信息不对称"——需求在传递中失真；新范式核心矛盾是"产出不一致"——多路AI各自生成、风格和逻辑可能对不上。协作重心从"信息传递"变成"约束对齐"。

目标优先级模型变化

旧范式优先级公式
优先级 = 目标价值 ÷ (人天 × 实现时间)
  • 成本固定：几个人、多少天，估算精度高，排期就是排人头。
  • 成本不需控制：申请→评审→达成一致即可，反正最终按人头计费。
  • RICE / ICE 用于说服团队：优先级评分本质是向工程团队证明"为什么先做这个"。
  • ROI 可预估：投入多少工时、预期产出多少功能，比值清晰可算。
新范式优先级公式
优先级 = 目标价值 ÷ (时间 + Token成本 + 对齐成本)
  • Token成本变动：一次生成可能$0.1，但迭代10次就是$10，成本随质量要求浮动，不再线性。
  • 对齐成本隐性：多人各自带AI产出不一致，返工的代价不显式但可能比生成成本高得多。
  • 成本难预估：AI产出速度和质量波动大，同一条任务可能5分钟也可能50分钟，估不准。
  • 新策略：方向大致正确，组织持续迭代活跃——只要团队在动、产出在迭代，方向可以边走边修。
  • 不再排人头：瓶颈从"几个人"变成"对齐质量+Token预算+上下文长度"，优先级是约束优化问题。
类比：旧范式像建楼——精确计算、按图纸施工，每一层都定型；新范式像有机生长——方向大致正确、边长边调，关键是保持迭代活跃度，让组织一直在长。

不是单人闭环：AI时代依然有多人协作

AI时代不是PM一个人+AI搞定一切。团队里依然有PM、设计师、前端工程师，每个人都带着自己的AI Agent。协作从"线性串联"变成"并行AI增强"——信息不对称降低了，但产出一致性要求升高了。下面的表梳理了哪些产出物被"回轻"（变轻但没消失），以及为什么多人协作仍然需要它们。

Sprint计划 每2周排Sprint + 估点 + 分配任务 里程碑看板（谁负责哪个模块 + AC完成率 + 依赖关系） 从精细排期 → 按模块分工 + 看AC完成率 多人各自带AI产出时仍需知道谁做哪个模块、依赖关系

被淘汰产出物的共性：桥梁型（人给人传递信息的中间产物）、过程管理型（为了管理多人协作流程而存在）、重复描述型（被更高保真的产出物自动包含）。AI时代协作核心矛盾从"信息传递"变成"约束对齐"——回轻了的产出物，本质都变成了对齐工具。
CHAPTER 02

思维范式：价值模型、成本结构与资产定义的变迁

本章节梳理6个维度的范式变化。每个维度按"旧范式→新范式"对照展开，帮助产品经理识别哪些思维惯性需要调整。

旧 · 价值模型

抓住用户心智入口 → 边际成本无限趋近0 → 后期商业化

先免费做大用户量，用户即生产资料即资产，后期通过广告/增值服务/数据变现。规模效应是核心壁垒，DAU就是生命线。

↓
新 · 价值模型

场景落地深度 → 边际成本正相关 → 即时价值交付

AI调用是有成本的（Token），每多一个用户多一份成本。不能再用"先免费后变现"的逻辑。每个用户必须即时产生价值，或贡献数据/场景反哺模型。用户量不再是唯一目标。

旧 · 边际成本

边际成本 → 0

软件开发一次，复制无限份，边际成本趋近0。用户越多，单位成本越低，规模效应越强。这是软件行业最根本的商业逻辑。

↓
新 · 边际成本

边际成本 ∝ 使用量

AI产品的每次调用都消耗Token/算力。用户越多，成本越高。必须确保每次调用的价值 > Token成本，否则用户越多亏越多。这是AI产品与传统软件最本质的商业差异。

旧 · 资产定义

用户量 = 资产

DAU/MAU是核心指标。用户就是生产资料，用户数据可以后期变现。先圈地后赚钱，用户规模即护城河。

↓
新 · 资产定义

数据 + 落地场景 = 资产

用户量不再是唯一壁垒。真正的资产是：①独家数据（让AI越用越准）②落地场景（让AI嵌入不可替代的工作流）。没有场景的AI产品，用户随时可迁移。

旧 · 壁垒来源

网络效应 + 规模效应

用户越多价值越高（网络效应），成本越低（规模效应），形成双轮飞轮。用户规模即壁垒。

↓
新 · 壁垒来源

数据飞轮 + 场景嵌入深度 + 工作流锁定

用户越用AI越懂用户（数据飞轮），AI嵌入越深切换成本越高（场景锁定）。没有数据和场景的AI产品，底层模型一升级就归零。

旧 · PM核心能力

需求洞察 + 沟通协调 + 项目管理

PM的价值在于：发现用户需求、翻译给工程师、协调多角色推进、控制进度风险。核心是"描述+协调"。

↓
新 · PM核心能力

问题框定 + 约束定义 + 验证判断 + 迭代节奏

PM的价值在于：框定正确的问题、定义AI的约束边界、验证AI产出的质量和方向、控制迭代节奏防止偏移。核心是"约束+验证"。

旧 · 思考模型

描述型思维——"用户应该能做什么"

PRD描述功能列表、用户故事描述需求、线框图描述布局。核心是"描述清楚让别人执行"，产出物是给人看的沟通文档。

↓
新 · 思考模型

约束型思维——"系统不允许做什么 + 必须遵守什么"

AGENTS.md定义技术约束、Design Tokens定义视觉约束、BDD定义行为边界。核心是"围栏比方向更重要"——AI自己会想怎么做，你定义什么不能做。

CHAPTER 04

变更管控：锚点层 · 进度层 · 执行层

产出物按变更频率分三层管理。每层有不同的管控机制和防偏移策略。本章节还包含SDD/BDD/TDD/ADR四个概念在新范式中的具体角色。

A

锚点层 — 极少变动，一改全局对齐

变更频率 2-3次/项目

定义项目"身份"的产出物，是所有下游产出的参照系。变更触发全局重新校验——就像 git rebase，基准变了所有下游都要 rebase。

Problem Framing 设计简报 ADR AGENTS.md Design Tokens 基线 数据模型基线
管控机制：任何变更触发全局偏移检测 → AI 对照新锚点检查所有已完成代码/设计 → 输出 deviations 清单
P

进度层 — 随进度增长，增量变更为主

每迭代增量追加

随功能推进而增加，主要是"加法"不是"减法"。已有条目通常不改，只追加新条目。改存量 = 改需求。

用户故事 (JTBD) Sitemap (增页面) Flow 图 (增路径) BDD 场景 (增行为) 异常态矩阵 (增状态) TDD 测试 AC Trace Matrix
增量校验：与锚点层一致，不动存量。已有 BDD 场景和测试一旦写好不轻易改——改 BDD 场景 = 改需求，需同步更新代码和测试
E

执行层 — 持续变动，高频迭代

每 session

日常与 AI 交互的产物，变动频率最高。不需要严格管控，但需定期归档提炼有效信息到进度层。

对话日志 代码版本 临时上下文片段 Design QA 发现项 调试记录
定期归档：每完成一个功能模块，把执行层有效信息（新边界条件、QA 发现、调试经验）提炼固化为进度层条目

防止预期偏移的5个机制

机制 作用层 触发时机 具体做法 检测什么偏移
锚点校验 锚点层→全链路 锚点层任何文件变更时 让 AI 读取新锚点文件逐项检查所有已完成代码/设计是否符合新约束，输出 deviations 清单 约束偏移（技术栈/架构/视觉规范）
BDD 回归测试 进度层→执行层 每次代码变更后 BDD 场景转化的测试自动运行，失败即偏移 行为偏移（功能行为变了）
快照对比 全层 每个里程碑 保存全链路快照（简报+ADR+Tokens+Sitemap+Flow+BDD+代码），下个里程碑对比变更 任何层面的偏移
Design QA 执行层 每屏/每组件完成后 对照 Design Tokens 逐项检查间距/颜色/字体/圆角/阴影/图标/交互态/状态完整性 视觉偏移
AC 追溯 进度层 每功能完成后 读取该功能 BDD 场景，逐条标注已实现/未实现/部分实现 功能完整度偏移

SDD / BDD / TDD / ADR 在新范式中的角色

概念 全称 传统角色 新范式角色 变更层级 防偏移作用
SDD Spec Driven Development 规格先行，代码跟着规格走 规格即源头：设计简报+ADR+Design Tokens+BDD 场景共同构成 spec，AI 从 spec 生成代码 锚点层+进度层 spec 不变则产出不变，spec 变了则产出跟着变
BDD Behavior Driven Development PM/Dev/QA 协作写 Given/When/Then PM 独自写 BDD 场景，AI 转化为测试+代码，BDD 场景 = 可执行的 PRD 进度层 测试挂了 = 行为偏移了
TDD Test Driven Development 先写测试再写代码 PM 定义测试意图 → AI 生成测试 → AI 生成代码让测试通过 进度层 测试是行为契约的守护者
ADR Architecture Decision Records 工程团队记录架构决策 PM 自己记录每个技术选型的决策+上下文+约束+后果 锚点层 防止"忘了当初为什么这么选"，防止随手改技术栈
防偏移本质：确保流动的东西不侵蚀增长的边界，确保增长的东西不偏离不变的基准。锚点层定义"不变的"，进度层定义"在增长的"，执行层定义"在流动的"。
CHAPTER 04b

Agent记忆与状态管理

Agent跨session如何保持状态？静态文件（AGENTS.md/ADR）覆盖了一部分，但不够。Agent需要三类记忆系统。

S

短期记忆 — 当前session的上下文

生命周期：单次session

Agent在单次对话中积累的上下文。包括当前正在做的功能、已生成的代码、已发现的问题。session结束后清除。对应执行层的对话日志。

当前功能上下文 已生成代码片段 本次session的调试记录 临时约束提醒
管控：不需要持久化。但如果session中做了重要决策，应在结束前提炼到ADR或BDD场景中。
L

长期记忆 — 跨session的项目决策历史

生命周期：永久

跨session保持的项目级决策和约束。AGENTS.md（技术约束）、ADR（架构决策记录）、Design Tokens（视觉规范）共同构成Agent的长期记忆。每次新session启动时，Agent优先加载这些文件。

AGENTS.md ADR记录 Design Tokens基线 数据模型基线 Problem Framing
管控：对应锚点层。变更频率极低，变更触发全局校验。关键是：Agent每次新session必须重新读取这些文件，不能假设"上次的记忆还在"。
W

工作记忆 — 当前项目做到哪了

生命周期：跨session但动态更新

记录项目的进度状态。哪些功能已完成、哪些BDD场景已通过、哪些异常态已覆盖。AC Trace Matrix是工作记忆的核心载体——它告诉Agent"接下来该做什么"。

AC Trace Matrix BDD场景完成状态 Sitemap页面完成状态 异常态矩阵覆盖状态
管控：对应进度层。每次session开始时Agent读取工作记忆确定当前进度，每次session结束时更新工作记忆。
Agent记忆与三层管控模型的映射：短期记忆=执行层、长期记忆=锚点层、工作记忆=进度层。Agent不需要额外的记忆系统，但需要确保每类记忆有明确的加载时机和更新规则。
CHAPTER 04c

Eval体系：AI产出质量评估

BDD/TDD是功能测试（pass/fail），但AI产出还有大量质量维度无法用pass/fail衡量。需要建立多维Eval体系。

Eval维度矩阵

评估维度 评估方式 工具/方法 频率 pass标准
代码质量 AI静态分析（ESLint/SonarQube）+ 复杂度检查 ESLint规则集+圈复杂度阈值 每次代码生成 0 error, complexity < 15
UI还原度 Design QA对照Design Tokens逐项检查 Design QA Checklist 每屏完成后 偏差 < 3项/屏
交互体验 可用性测试（原型验证） 5人可用性测试 每里程碑 完成率 > 80%, 无严重问题
安全性 自动化安全扫描 npm audit + 代码模式匹配 每次代码生成 0 高危漏洞
一致性 锚点校验（代码是否符合AGENTS.md） AI对照AGENTS.md逐项检查 锚点变更时 0 deviations

Eval流水线设计

Eval不是一次性检查，而是贯穿整个开发流程的自动化流水线。每次Agent生成代码后自动触发功能测试（BDD/TDD）+ 代码质量扫描；每屏完成后触发Design QA；每个里程碑触发全量Eval（含交互体验和安全扫描）。

阶段 触发时机 自动化项 人工项 产出物
即时Eval 每次代码生成 BDD测试+ESLint+安全扫描 无 测试报告+代码质量报告
屏级Eval 每屏完成后 Design QA自动化检查 视觉走查确认 Design QA Report
里程碑Eval 每个里程碑 全量回归+安全扫描+性能检测 交互体验测试+复盘 Snapshot Diff+Retro Report
Eval体系的核心原则：功能测试自动化（BDD/TDD），质量评估半自动化（Design QA自动检查+人工确认），体验评估人工为主（可用性测试）。不要试图把所有Eval都自动化，也不要完全依赖人工检查。

工作流：线性瀑布与并行AI增强的对照

旧范式：线性瀑布

6 个角色串联 · 每级等待 · 信息逐级损耗 · 周期 2-4 周

CHAPTER 05b

Multi-Agent编排：何时用单Agent vs 多Agent

手册前面的工作流假设PM+单个AI Agent。但实际项目中多Agent系统往往更高效。本章节给出单/多Agent的决策框架和编排模式。

场景 推荐模式 原因 编排复杂度
单功能模块开发（1-3屏） 单Agent 上下文简单，单Agent足够，多Agent反而增加协调成本 低
多功能并行开发（3+模块） 多Agent（并行） 模块间独立，并行产出效率高 中
复杂功能需多步推理 多Agent（流水线） 规划→编码→审查→测试，每步由专门Agent负责 中高
大型项目全栈开发 多Agent（并行+流水线） 前端/后端/数据并行，每条线内部流水线 高
探索性原型/MVP 单Agent 快速试错，不需要分工 低

多Agent编排的三种模式

模式1：流水线编排

结构：Planner Agent → Coder Agent → Reviewer Agent → Tester Agent

适用：复杂功能需多步推理

上下文传递：上游Agent的产出作为下游Agent的输入。关键是：每个Agent只接收它需要的上下文片段，不是全量传递。

风险：上下文在传递中丢失。对策：用结构化文件（BDD场景/ADR）作为Agent间的交接物，不依赖对话传递。

模式2：并行编排

结构：Agent A做前端 + Agent B做后端 + Agent C做数据层，同时进行

适用：多功能并行开发

上下文传递：所有Agent共享锚点层（AGENTS.md/Design Tokens/ADR），各自独立工作。

风险：产出不一致。对策：锚点层必须先定义清楚，定期对齐校验。

模式3：混合编排

结构：先并行（多个模块同时做），再流水线（每个模块内部规划→编码→测试）

适用：大型项目

上下文传递：并行阶段共享锚点层，流水线阶段用结构化文件传递。

风险：复杂度高，协调成本大。对策：用AC Trace Matrix跟踪所有Agent的进度。

Multi-Agent编排的核心不是“用几个Agent”，而是“上下文怎么在Agent之间传递”。最佳实践：用文件传递（BDD/ADR/AGENTS.md），不用对话传递。文件是Agent间的通信协议。
CHAPTER 06

实操启动：最小化必备清单

以下三件事是启动AI Coding的最小化必备项。缺少任何一个会导致产出质量不可控。

1. 最佳实践协作流程

STEP 1 锚点层定义

PM写设计简报+ADR+AGENTS.md，设计师做情绪板→选定Design Tokens。一次性定义所有约束。

角色：PM DESIGNER AI
STEP 2 进度层拆解

PM拆用户故事(JTBD)+Sitemap+Flow+BDD场景+异常态矩阵。设计师做视觉系统。并行展开。

角色：PM DESIGNER AI
STEP 3 并行AI Coding

PM用AI生成前端+后端代码，设计师用AI做走查。BDD场景自动转测试。持续迭代。

角色：PM DESIGNER AI
STEP 4 校验+集成

锚点校验→BDD回归测试→Design QA→AC追溯。偏移项修复或固化为新BDD场景。

角色：AI PM
STEP 5 上线+复盘

AI生成发版说明。上线后AI实时数据追踪。里程碑做快照对比+Retro Report。

角色：AI PM

2. PM思维架构

01 约束型思维

不再描述"做什么"，而是定义"不做什么"和"必须遵守什么"。围栏比方向更重要——AI自己会想怎么做，你定义什么不能做。

02 验证型思维

不再靠"沟通消除歧义"，而是靠"测试+QA+校验"确保产出质量。验证比描述更重要——BDD测试挂了=偏移了。

03 迭代型思维

不再"写完PRD锁定"，而是"持续对话迭代"。文档是活的不锁定，但靠三层管控防偏移。

04 价值>成本思维

每次AI调用的Token成本必须小于它创造的价值。用户量不再是唯一目标，场景深度才是。

05 数据飞轮思维

产品设计要内置数据回流——用户越用AI越准。没有数据飞轮的AI产品，模型一升级就归零。

06 场景锁定思维

AI嵌入用户工作流越深，切换成本越高。追求"不可替代的工作流嵌入"而非"功能堆砌"。

3. 价值公式

产品价值 = (场景嵌入深度 × 数据飞轮强度) ÷ (Token成本 + 对齐成本)

场景嵌入深度：AI嵌入用户工作流的深度，越深切换成本越高

数据飞轮强度：用户使用产生数据→数据提升AI→AI提升体验→用户更多使用的循环强度

Token成本：AI每次调用的算力消耗，随用户量线性增长

对齐成本：多人AI协作时产出不一致的返工成本

核心结论：旧范式追求"用户量最大化"（用户=资产，边际成本→0）。新范式追求"场景深度×数据飞轮最大化 + Token成本最小化"（场景+数据=资产，边际成本正相关）。这是产品经理需要内化的根本性思维转变。

4. 最佳实践协作流程详解（产品/技术/AI/测试如何协作）

产品（PM）
PM
  • 定义问题（Problem Framing）
  • 定义约束（AGENTS.md、Design Tokens、BDD场景）
  • 做技术决策（ADR）
  • 验证产出（AC Trace、Design QA）
  • 控制迭代节奏（三层管控）
技术（工程师）
TECH
  • AI从约束文件读取规范，在框架内生成代码
  • 工程师（如有）做架构Review和关键逻辑把关
  • 负责部署和基础设施
  • AI从BDD场景自动生成测试
AI（Agent）
AI
  • 从锚点层文件读取约束，在框架内生成代码
  • 从BDD场景自动生成测试断言
  • 从Design Tokens生成视觉一致的UI
  • 执行偏移检测（对照锚点检查已完成的代码）

  • Design QA走查→AI对照Design Tokens检查

  • 偏移项修复或固化为新BDD场景（防止复发）
CHAPTER 06b

上下文工程：如何把产出物喂给Agent

手册讲了14种产出物，但没讲怎么把它们塞进Agent的上下文窗口。一个项目的AGENTS.md+ADR+Design Tokens+BDD+Sitemap+Flow+异常态矩阵加起来可能超过20K tokens。需要上下文工程。

上下文预算分配

上下文层 加载策略 内容 估算Token 加载时机
always-in（常驻上下文） 每次对话都加载 AGENTS.md + Design Brief + 当前功能的BDD场景 3-5K session开始时自动加载
on-demand（按需加载） Agent判断需要时加载 Sitemap + Flow + 异常态矩阵 + 其他功能BDD 5-10K Agent在生成代码时按需读取
RAG检索 向量检索相关片段 ADR库 + 历史对话日志 + 调试记录 1-2K/次 Agent需要回溯决策时检索

上下文优先级矩阵

产出物 优先级 加载策略 备注
AGENTS.md P0 必须常驻 always-in Agent每次生成代码的约束框架

当前功能BDD场景 P0 必须常驻 always-in 当前功能的行为规格

Flow图 P1 生成多屏时加载 on-demand 只在生成/修改交互流程时需要
异常态矩阵 P1 生成异常态时加载 on-demand 只在生成空/错误/加载等状态时需要
ADR库 P2 按需检索 RAG 只在需要回溯技术决策时检索

上下文压缩策略

当BDD场景列表超过50条时，全部加载到上下文中不现实。需要压缩策略：

  • 摘要压缩：将已完成功能的BDD场景压缩为一行摘要（“登录功能：5个BDD场景已全部通过”），只展开当前正在做的功能
  • 分区加载：按模块分区，只加载当前模块的BDD场景
  • 递进加载：先加载BDD场景标题列表，Agent需要细节时再展开具体场景

跨模型适配

模型 上下文窗口 always-in容量 策略
GPT-4o 128K 可放全部产出物 但仍建议只放always-in，剩余on-demand减少干扰
Claude 3.5 Sonnet 200K 可放全部产出物 同上，上下文越长不代表效果越好
Qwen-max 32K 只能放AGENTS.md+Brief+当前BDD 需要更积极的压缩和RAG
本地开源模型 4K-8K 只能放AGENTS.md摘要 必须用RAG，且AGENTS.md需压缩
上下文工程的核心原则——不是“把所有东西都塞进去”，而是“在正确的时机加载正确的上下文”。上下文越长不代表效果越好，无关上下文反而会干扰Agent判断。always-in最小化，on-demand+RAG覆盖其余。
CHAPTER 06c

模型选择与Token经济学

手册全程说"AI"但没区分模型。不同模型的成本、质量、延迟差异巨大。PM需要模型选择策略和Token成本管理方法。

模型选择矩阵

任务类型 推荐模型档位 成本量级 质量要求 延迟要求
代码生成（核心逻辑） 前沿模型（GPT-4o/Claude 3.5/Qwen-max） $0.01-0.05/次 高 可接受5-10s
代码生成（样式/布局） 中等模型 $0.002-0.01/次 中 <5s
测试生成（BDD→测试代码） 中等模型 $0.002-0.01/次 中 <5s
Design QA（视觉检查） 多模态模型 $0.01-0.03/次 高 可接受10s
偏移检测（对照锚点检查） 前沿模型（需长上下文） $0.02-0.08/次 高 可接受15s
文档/发版说明 轻量模型 $0.001-0.005/次 低 <3s

模型路由策略

模型路由的核心思想——简单任务用便宜模型，复杂任务用贵模型。在AGENTS.md中定义路由规则，让Agent（或编排层）根据任务类型自动选择模型。

任务特征 路由到 判断依据
涉及核心业务逻辑/架构决策 前沿模型 影响范围大，质量要求高
涉及UI样式/布局调整 中等模型 有Design Tokens约束，质量要求中等
涉及测试/文档/简单CRUD 轻量模型 模式化任务，不需要强推理
需要视觉理解（Design QA） 多模态模型 需要图片输入能力

Token经济学

策略1：Token预算分配
每个功能模块分配Token预算。例如：简单页面2K tokens预算，复杂功能5K tokens预算。超出预算时暂停迭代，评估是否方向跑偏。
策略2：缓存策略
AI生成的Design Tokens解析结果、BDD场景到测试代码的转换结果、Sitemap到路由代码的转换结果——这些是确定性的，可以缓存。同一个BDD场景不需要每次都重新生成测试代码。
策略3：Prompt优化
AGENTS.md和BDD场景用结构化格式（JSON/YAML）而非自然语言段落，减少Token消耗。一个结构化的BDD场景约200 tokens，自然语言描述同一行为可能500+ tokens。
策略4：增量生成
不要每次让Agent从头生成整个文件。用Edit模式修改现有文件，而不是Write模式重写。增量修改的Token消耗是全量生成的1/5到1/10。
Token经济学的核心原则——不是"省Token"，而是"每个Token创造的价值最大化"。用便宜模型处理简单任务省下的预算，留给前沿模型处理复杂任务。预算控制的目标是防止无限迭代（屎山循环），不是压缩质量。
CHAPTER 06d

Human-in-the-loop：人工介入节点设计

不是所有环节都应该自动化。PM需要明确哪些环节必须人工审查、审查什么、何时审查。

节点 触发条件 审查内容 人工/自动 不审查的风险
锚点层变更 AGENTS.md/ADR/Design Tokens修改 变更影响范围评估 人工必须审查 变更影响下游全部产出，不审查=全局偏移
代码生成后 每次Agent生成代码 BDD测试是否通过+安全扫描 自动检查+人工确认 自动检查能覆盖功能和安全，但无法判断代码是否"优雅"
每屏完成后 Design QA触发 视觉还原度+状态完整性 自动检查+人工走查 自动检查能对齐Design Tokens，但无法判断交互体验
里程碑处 快照对比触发 全量回归+交互体验+方向校准 人工必须审查 方向是否偏移只有人能判断，AI无法自评方向
上线前 发版前 安全审计+合规检查+用户数据保护 人工必须审查 安全和合规问题AI可能遗漏

自动化边界：什么该自动，什么必须人工

应该自动化的

  • BDD场景→测试代码生成（模式化，AI擅长）
  • Design Tokens对齐检查（规则明确，适合自动化）
  • 代码安全扫描（规则明确）
  • AC Trace Matrix状态更新（数据聚合，适合自动化）
  • 发版说明生成（从git log提取）

必须人工的

  • 锚点层变更影响评估（需要判断力，AI无法自评）
  • 交互体验走查（"感觉对不对"AI判断不了）
  • 方向校准（"我们在做对的事吗"只有人能判断）
  • 安全合规审查（风险高，不能全靠AI）
  • 优先级决策（资源分配需要人的判断）
Human-in-the-loop的设计原则——自动化"规则明确的重复劳动"，人工保留"需要判断力的决策点"。不要试图自动化一切，也不要过度依赖人工。关键是找到每类任务的"自动化边界"。
CHAPTER 06e

生产部署与运维：Agent工作流的CI/CD

Agent工作流也需要持续集成/持续部署。Prompt变更如何灰度？Agent行为如何回归测试？如何监控偏移？如何回滚？

Agent工作流的CI/CD流水线

阶段 触发 自动化内容 人工确认 产出物
代码提交 git push BDD测试+ESLint+安全扫描 无 测试报告
Design QA 每屏完成 Design Tokens对齐检查 视觉走查 Design QA Report
锚点变更 AGENTS.md/ADR修改 全局偏移检测+影响范围分析 影响评估确认 偏移报告
里程碑 预设节点 全量回归+快照对比+交互测试 方向校准确认 Snapshot Diff
上线 发版触发 发版说明生成+安全审计 上线审批 Release Notes

版本管理

版本化对象 策略 工具 回滚方式
AGENTS.md/Prompt git版本控制+变更评审 Git branch+PR git revert回滚到上一版
Design Tokens git版本控制 Git branch 回滚Tokens+重新生成受影响UI
BDD场景 git版本控制+测试结果绑定 Git branch+CI 回滚BDD+重新生成测试
Agent配置 配置文件版本化 JSON/YAML+git 切换到上一版配置

监控与告警

监控项 指标 告警阈值 告警方式
Token消耗异常 每功能模块Token消耗 超预算150% 通知PM暂停迭代
测试通过率下降 BDD测试通过率 连续3次<90% 通知PM检查代码质量
AC完成率停滞 AC Trace完成率 连续2天无进展 通知PM检查blocker
偏移检测 锚点校验deviation数 >5项/次 通知PM做全局校验

回滚策略

回滚策略按影响范围分三级：

  • 功能级回滚：单个功能模块有问题→git revert该功能代码+BDD场景，不影响其他模块
  • 屏级回滚：某屏Design QA不通过→回滚该屏代码+重新生成，不影响其他屏
  • 锚点级回滚：锚点层变更有问题→回滚锚点文件+全量重新校验+受影响模块全部重做
生产部署的核心原则——把Agent工作流当作软件工程对待，用CI/CD的纪律管理Prompt/Token/产出版本。不要因为"AI生成的"就放松工程标准。Agent不是人，不会自觉遵守规范——你需要CI/CD来强制。
